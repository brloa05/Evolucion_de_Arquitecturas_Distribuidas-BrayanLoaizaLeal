Recorrido por las 6 arquitecturas

Parte I — TCP Sockets

Comunicacion de bajo nivel mediante sockets. El servidor acepta conexiones, lee texto plano y responde. Sin protocolo estandarizado, logica manual de parsing.

Puertos: 35000 / 31000

Parte II — HTTP

Protocolo estandar sobre TCP. Rutas, metodos GET/POST y codigos de estado. El cliente puede ser cualquier navegador o herramienta REST.

Puertos: 8080 / 8081

Parte III — RMI

Invocacion remota de metodos Java. El cliente llama metodos como si fueran locales. Fuertemente tipado pero acoplado a la JVM.

Puertos: 23000 / 24000

Parte IV — gRPC

Contratos en Protocol Buffers (.proto). Alta eficiencia con HTTP/2, tipado fuerte, generacion automatica de stubs en cualquier lenguaje.

Puertos: 50051 / 50052

Parte V — Microservicios

Cada responsabilidad es un servicio independiente. Escalabilidad granular, despliegue autonomo. El cliente agrega multiples servicios.

Puertos: 50055 / 50056 / 50060 / 50061

Parte VI — API Gateway

Punto unico de entrada HTTP. Oculta la complejidad interna, agrega servicios, maneja enrutamiento y puede incorporar autenticacion centralizada.

Puertos: 8090 / 8091 / 8095

Patron API Gateway — Ventajas y Desventajas

Ventajas

  • Punto de entrada unico para los clientes
  • Oculta la topologia interna de microservicios
  • Centraliza autenticacion, logging y rate limiting
  • Reduce el numero de llamadas del cliente
  • Permite evolucion independiente de servicios internos

Desventajas

  • Punto unico de fallo si no hay redundancia
  • Latencia adicional por la capa extra de enrutamiento
  • Mayor complejidad operacional
  • Puede convertirse en un cuello de botella
  • Logica de agregacion puede volverse compleja

Reflexion Final

A lo largo de este taller pude observar como la necesidad de mayor abstraccion, escalabilidad y mantenibilidad impulsaron la evolucion de las arquitecturas distribuidas. Comenzar con TCP Sockets me permitio entender la base de toda comunicacion en red: bytes viajando por un canal bidireccional, sin ninguna convencion sobre como interpretarlos.


La transicion a HTTP introdujo el primer contrato comun: verbos, rutas y codigos de estado. Con RMI se logro una abstraccion mayor al invocar metodos remotos como si fueran locales, pero al costo de quedar atado a la JVM y a la serializacion de Java.


gRPC resolvio ese acoplamiento tecnologico usando Protocol Buffers como contrato independiente del lenguaje, y HTTP/2 para mayor eficiencia. A partir de ahi, los microservicios permitieron dividir el dominio en unidades deployables independientemente, cada una con su propio ciclo de vida.


Finalmente, el API Gateway simplifica la perspectiva del cliente: en lugar de conocer la ubicacion de cada microservicio, solo necesita hablar con un unico punto de entrada. Cada capa de esta evolucion resuelve limitaciones de la anterior, pero a cambio introduce nuevos desafios operacionales. No existe una arquitectura universalmente superior; la eleccion depende del contexto, el tamano del equipo y los requisitos de escala del sistema.
